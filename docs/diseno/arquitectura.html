Flujo: llamar siguiente turno

El backend valida RN-03 y RN-02 antes de cambiar el estado. La pantalla pública se entera en la siguiente consulta, a más tardar en 3 segundos.

sequenceDiagram
    actor R as Recepcionista
    participant UI as RecepcionView (Vue)
    participant API as FastAPI /api/turnos
    participant S as turno_service
    participant DB as MySQL
    participant P as PantallaView (Vue)
    R->>UI: Clic "Llamar siguiente"
    UI->>API: POST /siguiente (Bearer JWT)
    API->>API: requiere_rol("RECEPCIONISTA")
    API->>S: llamar_siguiente(id_ventanilla)
    S->>DB: ¿turno LLAMADO abierto? (RN-03)
    S->>DB: SELECT turno EN_ESPERA más antiguo (RN-02)
    S->>DB: UPDATE estado = LLAMADO, hora_llamado
    API-->>UI: 200 {codigo: "C-015"}
    loop cada 3 s
      P->>API: GET /actual
      API-->>P: {codigo: "C-015", ventanilla: "Ventanilla 1"}
    end

Decisiones de diseño

Se priorizó lo que se puede construir y probar en una semana para el MVP.

DecisiónDescartadoMotivo
Vue 3 (SPA)HTML + JS sin framework, ReactComponentes reutilizables con curva de aprendizaje menor que React.
FastAPINode + Express, DjangoValidación con Pydantic y Swagger automático, que apoya las pruebas y el manual técnico. Más liviano que Django.
Consulta cada 3 s en la pantalla públicaWebSocketsMás simple para el MVP y cumple RNF-02. FastAPI soporta WebSockets si se migra después.
JWTSesiones en servidorSin estado; rutas protegidas por rol con una dependencia de FastAPI.
Número por servicio y día en una transacción (SELECT … FOR UPDATE)Contador globalCumple RN-01 y evita números repetidos si dos kioscos generan turno a la vez.
SQLAlchemy ORMSQL escrito a manoMenos código repetido y consultas parametrizadas.
